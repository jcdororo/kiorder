# kiorder 팀 파이프라인

kiorder의 5개 역할을 정해진 순서로 소집해 하나의 작업을 PR까지 끌고 가는 절차다.
오케스트레이터(메인 세션)가 이 문서를 따라 각 단계를 진행한다.

## 실행 모드: 서브 에이전트

**이 환경에는 `TeamCreate`가 없다.** 따라서 팀 모드가 아니라 `Agent` 도구로 직접 호출하는 서브 에이전트 모드로 운영한다. 서브 에이전트는 형제끼리 통신할 수 없고 결과를 오케스트레이터에게만 반환하므로, 단계 간 인수인계는 **파일 기반 + 반환값**으로 한다.

`SendMessage`는 사용할 수 있다. 이미 스폰한 에이전트에게 이름으로 후속 질문을 보내면 **그 에이전트의 컨텍스트를 유지한 채** 이어서 답하게 할 수 있다. 사소한 되물음 때문에 새로 스폰해 백지부터 다시 읽히지 마라 — 비용이 몇 배 차이난다.

**모든 `Agent` 호출에 `model: "opus"`를 명시한다.**

## 에이전트 구성

| 에이전트 | 권한 | 역할 | 산출물 |
|---|---|---|---|
| `kiorder-planner` | 읽기 전용 | 범위 선별·정합성 검증 | 반환값 → `_workspace/1_plan.md` |
| `kiorder-frontend` | 전체 | 프론트 구현 | `_workspace/2_impl_frontend.md` |
| `kiorder-backend` | 전체 | 백엔드 구현 | `_workspace/2_impl_backend.md` |
| `kiorder-reviewer` | 읽기 전용 | 로직·보안·엣지케이스 | `ReportFindings` → `_workspace/3_review_code.md` |
| `kiorder-ux` | 전체(임시 스크립트용) | 실제 화면 검증 | `_workspace/3_review_ux.md` |

`planner`와 `reviewer`는 Write 툴이 **없다.** "리뷰만 하고 코드는 못 고침"을 도구 권한으로 강제하기 위한 의도된 설계다. 대신 이들의 반환값을 **오케스트레이터가 `_workspace/`에 기록한다.**

## 언제 팀을 소집하지 않는가 — 먼저 읽어라

서브 에이전트는 **격리에 값어치가 있을 때만** 부른다. 이 판단이 하네스의 핵심이고, 실적이 이를 뒷받침한다 — 지난 실행에서 6건 중 5건은 오케스트레이터가 직접 처리하는 편이 나았다.

**부를 이유가 있는 경우**
- 권한 격리가 의미 있을 때 — `reviewer`/`planner`는 Write가 없어 구조적으로 코드를 못 고친다
- 탐색량이 커서 본채 컨텍스트를 오염시킬 때 — `ux`는 스크린샷 여러 장과 파일 다수를 뒤진다
- 서로 다른 파일을 동시에 만드는 병렬 작업일 때

**부르지 말 것**
- 단일 파일 순차 수정, 한두 줄 고치기 → 오케스트레이터가 직접 한다
- 파이프라인 전체가 과한 작업 → **필요한 단계만 골라 쓴다. 5단계를 항상 다 돌 필요는 없다**

**근거**: `ux` 1회 실행에 약 9만 토큰이 든다. 팀 소집은 공짜가 아니다. "팀을 꾸릴 수 있다"보다 **"언제 꾸릴 가치가 있는지 판단할 줄 안다"**가 실제 역량이다.

## 워크플로우

```
[0 컨텍스트]  기존 산출물 확인 → 초기/후속/부분 재실행 판별
[1 준비]      브랜치 생성 + _workspace/
[2 기획]      planner
   ◆ 사람 판단 체크포인트 ◆
[3 구현]      frontend ∥ backend
[4 검증]      reviewer ∥ ux  (병렬)
   ◆ 사람 판단 체크포인트 ◆
[5 반영]      수정 → 커밋 → PR → 리뷰를 PR 코멘트로
[6 정리]      CI 확인 + 요약 보고
```

### Phase 0: 컨텍스트 확인

1. `_workspace/` 존재 여부를 확인한다
2. 실행 모드를 판별한다
   - **미존재** → 초기 실행. Phase 1로
   - **존재 + 부분 수정 요청**("리뷰만 다시", "UX만 다시") → **부분 재실행.** 해당 에이전트만 재호출하고 이전 산출물 경로를 프롬프트에 넣는다. Phase 1을 건너뛴다
   - **존재 + 새 작업 요청** → **새 실행.** 기존 `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮긴 뒤 Phase 1로
3. 부분 재실행이면 에이전트에게 **"이전 결과를 읽고 지적된 부분만 고쳐라"**를 명시한다. 전체 재분석은 낭비다.

### Phase 1: 준비

1. 작업 성격에 맞는 브랜치를 만든다 — `feat/` `fix/` `refactor/` `chore/`. **`main`에서 직접 작업하지 않는다.**
2. `_workspace/` 생성 (gitignore 대상이므로 커밋되지 않는다)
3. 요청 원문을 `_workspace/0_request.md`에 저장한다 — 에이전트들이 참조할 원본이다

### Phase 2: 기획

`kiorder-planner`를 호출한다. `_workspace/0_request.md`를 읽으라고 프롬프트에 명시한다.
여러 항목을 처리할 때는 **우선순위 선별까지** 시킨다.

반환값을 `_workspace/1_plan.md`에 기록한다(planner는 Write가 없다).

### ◆ 체크포인트 1 — 사람이 결정한다

기획 결과를 사용자에게 보여주고 **무엇을 할지 직접 고르게 한다.** 자동으로 다음 단계로 넘어가지 않는다.

> 이 체크포인트를 없애면 안 된다. 이 프로젝트의 목표는 "AI가 뭘 했나"가 아니라 **"내가 어떤 판단을 했나"**를 남기는 것이고, 전 과정을 자동화하면 그 기록 자체가 사라진다. 자동화의 상한을 의도적으로 정하는 것이 이 하네스의 설계 의도다.

### Phase 3: 구현

승인된 범위만 구현시킨다. `_workspace/1_plan.md`를 먼저 읽으라고 지시한다.

**병렬 규칙 — 실제로 충돌났던 부분이다.** 서로 다른 파일을 만드는 작업만 병렬로 돌린다. **같은 파일을 여러 에이전트가 동시에 수정하면 서로 덮어쓴다.** 신규 파일 생성은 병렬, 기존 파일에 연결하는 작업은 오케스트레이터가 직접 순차 처리한다.

`frontend`와 `backend`는 다른 디렉터리를 만지므로 병렬 안전하다. 단 **백엔드가 API 시그니처를 바꾸면 프론트가 그 위에 의존**하므로, 그 경우엔 backend 먼저 → frontend 순서로 돌린다.

### Phase 4: 검증 (병렬)

관점이 달라 서로 간섭하지 않으므로 **한 메시지에서 `kiorder-reviewer`와 `kiorder-ux`를 동시에 호출**한다(`run_in_background: true`).

- `reviewer` — 코드. **타입·린트·빌드는 CI가 하므로 검사시키지 않는다**
- `ux` — 렌더된 실제 화면. 코드로는 못 잡는 것(리스트 재정렬, 죽은 어포던스, 잘린 레이아웃)

화면 변경이 없는 작업(백엔드 전용, 설정 변경)이면 **`ux`를 부르지 않는다.** 9만 토큰을 아낀다.

### ◆ 체크포인트 2 — 사람이 결정한다

지적 중 **무엇을 반영할지 사용자가 고른다.** 리뷰어 제안을 그대로 적용하지 말고, 그 제안이 깨뜨리는 다른 케이스가 없는지 먼저 따진다.

> 실제 사례: 리뷰어가 폼 리셋에 `key={editingItem?.id ?? "new"}`를 제안했으나, 그대로 쓰면 "추가 다이얼로그를 열었다 닫고 다시 열기"에서 id가 같아 리마운트가 안 되는 새 회귀가 생겼다. **표준 패턴이라고 검증 없이 적용하지 않는다.**

### Phase 5: 반영 → 커밋 → PR

1. 승인된 지적을 반영한다. 한두 곳이면 직접, 여러 파일이면 구현 에이전트에 재위임(이전 산출물 경로 전달)
2. 검증: `cd frontend && npx tsc --noEmit && npm run lint` / 백엔드를 건드렸으면 `npx prisma generate && npm run build`
3. 커밋을 **성격별로 분리**한다 — 하네스/설정은 `🔧 chore`, UI 버그는 `🐛 fix`, 구조 개선은 `♻️ refactor`. 형식은 `CLAUDE.md` 규칙을 따른다
   > 여러 줄 한글 메시지는 PowerShell here-string이 깨진다. 파일로 써서 `git commit -F`를 쓴다
4. push → `gh pr create`. PR 본문에는 **"왜"**를 쓴다
5. **리뷰 결과를 PR에 남긴다:**
   ```
   gh pr comment {번호} --body-file _workspace/3_review_code.md
   gh pr comment {번호} --body-file _workspace/3_review_ux.md
   ```
   `_workspace/`는 커밋되지 않고 사라지지만 PR 코멘트는 영구히 남는다. **리뷰가 기록으로 남는 것이 이 파이프라인의 산출물 중 하나다.**

### Phase 6: 정리

1. CI 확인 — `gh pr checks {번호}`. 빨간불이면 고치고 다시 push한다
2. `_workspace/`는 **지우지 않는다**(사후 추적용, gitignore라 커밋 안 됨)
3. 사용자에게 요약 보고: 무엇을 했고, 무엇을 안 했고, 어떤 판단이 사람에게 넘어갔는지

## 데이터 흐름

```
0_request.md
    ↓ (planner가 Read)
반환값 → 오케스트레이터가 기록 → 1_plan.md
    ↓ (frontend/backend가 Read)
2_impl_frontend.md · 2_impl_backend.md
    ↓ (reviewer/ux가 Read + git diff)
3_review_code.md · 3_review_ux.md
    ↓
gh pr comment (영구 기록)
```

**핵심**: 서브 에이전트는 이전 대화를 전혀 모른다. 프롬프트에 **"이 파일을 먼저 읽어라"**를 명시하는 것이 유일한 인수인계 수단이다. 빠뜨리면 에이전트가 백지에서 추측한다.

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 에이전트 1개 실패 | 1회 재시도. 재실패면 **누락을 명시하고** 나머지로 진행. 조용히 건너뛰지 않는다 |
| 에이전트가 범위를 벗어난 수정 | `git diff`로 확인 후 범위 밖 변경을 되돌린다. 리뷰어가 이를 결함으로 지적하는 것이 정상이다 |
| `ux`가 화면을 못 봄 | 백엔드 콜드스타트 의심 → 재시도. 그래도 안 되면 **"검증 못 함"으로 보고한다.** 코드만 보고 판단한 결과를 화면 검증인 것처럼 보고하지 않는다 |
| 리뷰 지적이 서로 상충 | 삭제하지 말고 **양쪽을 출처와 함께 병기**해 사용자에게 판단을 넘긴다 |
| CI 빨간불 | 로그를 읽고(`gh run view --log-failed`) 고친다. `--no-verify`로 우회하지 않는다 |
| 같은 파일 동시 수정 충돌 | 병렬 위임 자체가 잘못된 것이다. 되돌리고 순차로 다시 한다 |

## 테스트 시나리오

**정상 흐름**
1. 사용자가 "메뉴 관리 화면 UX 지적 6건 처리해줘" 요청
2. Phase 1에서 `fix/owner-menu-ux` 브랜치 + `_workspace/` 생성
3. Phase 2에서 `planner`가 6건을 코드로 검증 → 2건은 이미 해결됨, 2건은 단일 원인으로 판명 → P0 3건 제안
4. 체크포인트 1: 사용자가 3건 중 2건 선택
5. Phase 3에서 `frontend`가 구현 (백엔드 변경 없으므로 `backend` 미호출)
6. Phase 4에서 `reviewer` ∥ `ux` 병렬 검증
7. 체크포인트 2: 사용자가 지적 4건 중 2건 반영 선택
8. Phase 5에서 반영 → 커밋 → PR 생성 → 리뷰 2건을 PR 코멘트로
9. Phase 6에서 CI 초록 확인 후 보고
10. 예상 결과: PR 1개, 코멘트 2개, `_workspace/` 산출물 5개

**에러 흐름**
1. Phase 4에서 `ux`가 로그인 타임아웃으로 실패
2. 1회 재시도 → 백엔드 콜드스타트로 판명, 재시도 성공
3. 재시도도 실패했다면: `reviewer` 결과만으로 체크포인트 2를 진행하되, **"UX 검증 미수행"을 보고서와 PR 코멘트에 명시**
4. 사용자가 UX 검증이 필수라고 판단하면 Phase 0의 부분 재실행으로 `ux`만 다시 호출

## 부분 재실행 예시

"UX 검증만 다시 돌려줘" →
Phase 0에서 부분 재실행으로 판별 → Phase 1~3 건너뜀 → `kiorder-ux`만 호출하며 프롬프트에 `_workspace/3_review_ux.md`를 읽고 **해결된 항목은 빼고 미해결·신규만** 보고하라고 지시 → 결과를 PR 코멘트로 추가.
